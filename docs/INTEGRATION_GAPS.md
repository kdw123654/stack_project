# STACK_BE 6142480 연동 현황

| 기능 | 프론트에서 사용하는 흐름 |
|---|---|
| 공고 링크 | B의 /job-postings/fetch로 본문을 받고 A의 분석 API 호출 |
| 공고 저장 | A 분석 원본을 B에 전달하고 B 공고 ID를 사용. 사용자 문항 수정은 별도 PATCH |
| 자소서 저장 | B 공고 → 자소서 프로젝트 → 생성 답변 PUT → 편집 PATCH → 저장 상태 반영 |
| 포트폴리오 저장 | B 공고 → 포트폴리오 프로젝트 → A 생성 슬라이드 PUT → 편집 PATCH |
| 슬라이드 한 장 재생성 | A의 선택 슬라이드 재생성 → 성공 결과를 해당 슬라이드에 적용 → B의 generated PUT으로 저장 |
| 이미지 | 선택 파일 미리보기와 교체. B 저장 시 A 분석 이미지를 가져오거나 선택 파일 업로드 |
| PDF/PPTX | 현재 슬라이드와 이미지를 먼저 저장한 뒤 B export가 반환한 다운로드 URL 열기 |

A의 생성 원본과 사용자 편집 내용을 구분합니다. 프로젝트 ID를 최근 초안과 함께 보관해 저장 중 실패하면 같은 프로젝트에서 다시 시도합니다. 새 코드 이전에 만든 기기 초안에는 A 원본 식별자가 없어 새 공고 분석과 생성이 필요합니다.

## 서버 실행 조건

- 기존 Supabase DB에는 STACK_BE의 SQL 마이그레이션 04~07을 순서대로 적용합니다. 신규 DB는 최신 01_schema.sql을 기준으로 합니다.
- PDF 출력은 B 서버에서 LibreOffice와 한글 폰트를 사용합니다. 백엔드의 PORTFOLIO_EXPORT.md에 SOFFICE_PATH와 PORTFOLIO_FONT 설정이 있습니다.
- A에서 추출한 이미지가 만료된 경우 슬라이드에서 파일을 다시 선택할 수 있습니다. 브라우저에서 선택한 파일은 서버 저장 전까지 현재 화면에 유지됩니다.

## 남은 범위

실제 A/B 서버와 Supabase에서 로그인부터 PDF/PPTX 다운로드까지 확인이 필요합니다. 프론트에서는 모의 HTTP 응답 테스트와 빌드로 검증합니다. B에 저장된 전체 프로젝트 목록, A 분석 수정 이력, 운영용 A 인증·소유권·데이터 삭제 연계는 후속 작업입니다.
